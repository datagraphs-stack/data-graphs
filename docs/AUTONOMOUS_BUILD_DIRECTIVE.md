# Autonomous build directive — operating implementation

The Owner's complete 20-section directive is preserved in `commission/AUTONOMOUS_BUILD_2026-09-09.md` and governs this project. The following is the day-to-day cursor into that commission, not a replacement for it.

**STATE → SELECT → BUILD → TEST → REVIEW → INTEGRATE → VERIFY → RECORD → CONTINUE.** Autonomy is the default for ordinary authorized engineering. Read durable context before every significant implementation; select dependency-satisfied work that removes the current product constraint. Do not optimize for commit count or checklist completion.

## Execution

Build product machinery, not governance theater. A parser, crawler, archive or identity stage is proven by runtime evidence, first on fixtures and then on bounded real sources; a document is not a live capability. Preserve the Lab but do not spend the first campaign redesigning it.

Use technical lead/controller, acquisition, evidence, extraction, identity, graph, signals, product and review responsibilities when real parallel agents exist. Shared contracts have one owner. Parallelize independent tasks without inventing incompatible models. Never portray one model's self-review as independent review or claim that named agent roles are running when they are only responsibilities.

Fix normal test, TypeScript, schema, deployment-command and implementation failures without asking for another routine Owner approval. Continue through dependency-satisfied work until a genuine blocker, an unsafe authorization boundary or the active session boundary. A session is not an unattended background worker.

## Risk and authority

Ordinary reversible work, bounded non-production data, reviewed additive staging migrations, staging deployments/crawls and staging verification may proceed under existing policy. Preserve required reviews and branch protection.

Escalate applicable production deployments, DNS changes, real customer-data writes, paid commitments, destructive migrations, deletion of evidence, secret changes, irreversible identity merges, uncontrolled crawls and sensitive acquisition. Do not invent new Owner gates for unambiguous routine work. Do not alter permissions just to make a test pass.

**Conservative data authority + aggressive engineering progress.** Unknown remains unknown; malformed input is unclassified; unsupported extraction is a candidate; conflicting claims remain visible; missing evidence blocks publication, not independent engineering.

## First campaign and real-world proof

Source Registry → crawl mission schema → bounded crawler → raw archive → fingerprints/change detection → page classification → observations → company identity → product identity → relationships → repeat refresh → temporal events → coverage diagnostics → 100-company graph → public Market Graph → monitoring/signals.

Transition from fixtures to five real company domains as soon as acquisition policies and bounded execution exist. Later prove extraction across differently structured real pages, identity from real company/product records, and signals from two real observations. Never substitute synthetic changes for real-world signal proof.

## Feedback and continuity

PROJECT_STATE is a concise live cursor: built, deployed, proven/unproven, Git state, milestone, exact dependency/blocker and permitted independent work. Put long histories in ADRs, receipts and Git.

Track crawl coverage/failures/latency; extraction eligibility/yield/rejections; exact/candidate/unresolved identities and conflicts; graph entities/relationships/provenance/staleness; meaningful changes/events/reviewed false positives; product coverage/usefulness and real interactions. Use measurements to select subsequent tasks. No fabricated counters.

A blocker record includes milestone, exact error and evidence, last attempt, why unchanged retries are pointless, changed conditions required, whether Owner intervention is genuinely required and independent work available. Do not schedule hourly retries of the same failing operation.

The future mission runtime should acquire, archive, extract, resolve, compile, identify gaps, monitor and publish from a bounded mission. A persistent builder or scheduler must be explicitly installed and proven before claiming unattended progress. Current CI is test/build automation only; it does not generate code or crawl the web. Portfolio HQ reporting is future work when an integration actually exists; no integration or successful report is presumed.
